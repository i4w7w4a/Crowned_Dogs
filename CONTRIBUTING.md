# Работа вдвоём: GitHub и деплой Crowned Dogs

## Короткая схема

**Свежий `main` → своя ветка → маленькие коммиты → rebase на свежий `main` → проверки → Pull Request → merge → один деплой на VPS.**

- В `main` напрямую не коммитим и не пушим.
- Force push не используем: ни `push --force`, ни `push --force-with-lease`.
- Деплой делаем только после merge PR в `main`.
- Пароли VPS, `BOT_TOKEN`, `.env` и личные GitHub-токены в репозиторий не кладём.
- Один и тот же `.glb`, `.png`, `.webp`, `.mp3` одновременно меняет только один человек: Git не умеет смыслово объединять бинарные файлы.

## Роли

**Друг:** работает только с GitHub и своей локальной копией. Доступ к VPS и секретам бота ему не нужен.

**Владелец сервера:** проверяет PR, принимает их в `main` и запускает деплой. Эти же правила веток и проверок обязательны и для владельца.

# Инструкция для друга

## 1. Одноразовая настройка

1. Прими приглашение в приватный репозиторий `code-of-stalker/Crowned-Dogs` на GitHub.
2. Установи [GitHub CLI](https://cli.github.com/), Node.js 22.18+ и Rust через `rustup`.
3. Войди в GitHub и скачай проект:

```bash
gh auth login
gh repo clone code-of-stalker/Crowned-Dogs
cd Crowned-Dogs
```

4. Установи зависимости и собери WASM:

```bash
npm ci
rustup update stable
rustup target add wasm32-unknown-unknown
cargo install wasm-bindgen-cli --version 0.2.129 --locked
npm run rust:build
```

Полная справка по сборке находится в `LOCAL_BUILD.md`.

## 2. Начало каждой задачи

Сначала получи свежий `main`, затем создай отдельную ветку:

```bash
git switch main
git pull --ff-only
git switch -c friend/korotkoe-nazvanie
```

Примеры названий: `friend/beard-color`, `friend/battle-camera`.

**Не начинай новую работу от старой ветки или чужого непринятого PR.**

## 3. Во время работы

Делай небольшие законченные коммиты. Перед коммитом смотри, что именно попадёт в него:

```bash
git status
git diff
git add путь/к/нужному/файлу
git commit -m "Short English description"
```

Не используй `git add .` без предварительной проверки `git status`: так в коммит случайно попадают чужие черновики, сборки и секреты.

Если одновременно с тобой кто-то меняет соседние файлы, чаще сообщай, над чем работаешь. Особенно это важно для `package.json`, `package-lock.json`, `HANDOFF.md`, общих моделей и изображений.

## 4. Перед Pull Request

Получи свежий `main` и перенеси свои коммиты поверх него:

```bash
git fetch origin
git rebase origin/main
npm run check
npm run web:build
```

CI запускает Linux-проверки `check` и Windows-сборку `windows`. Локальные команды выше не заменяют CI, но заранее ловят большинство ошибок.

Если rebase остановился на конфликте:

1. Выполни `git status` и посмотри конфликтующие файлы.
2. Открой каждый файл, удали метки `<<<<<<<`, `=======`, `>>>>>>>` и вручную оставь правильный результат.
3. Не выбирай вслепую «наш» или «их» вариант: во время rebase смысл этих кнопок часто путают.
4. Для бинарного конфликта остановись и договорись с автором второй версии, какой файл должен остаться.
5. Затем продолжи:

```bash
git add путь/к/исправленному/файлу
git rebase --continue
```

Если что-то пошло не так, rebase можно полностью отменить до продолжения:

```bash
git rebase --abort
```

Когда проверки зелёные, отправь ветку и создай PR:

```bash
git push -u origin HEAD
gh pr create --base main --fill
```

В описании PR коротко укажи, что изменилось и как это проверить. Не отправляй PR друг на друга: цель всегда `main`.

## 5. После принятия PR

```bash
git switch main
git pull --ff-only
git branch -d friend/korotkoe-nazvanie
```

Удаляй локальную ветку только после того, как её изменения действительно вошли в `main`.

# Инструкция для владельца

## 1. Проверка и принятие PR

Посмотри изменения, результаты CI и комментарии второго разработчика:

```bash
gh pr list
gh pr view НОМЕР
gh pr diff НОМЕР
gh pr checks НОМЕР
```

Не принимай PR с красными или ещё идущими проверками. Если `main` успел обновиться, автор сначала делает rebase и повторяет проверки.

Принятие идёт через squash или rebase, чтобы история `main` оставалась линейной:

```bash
gh pr merge НОМЕР --squash
```

Перед merge в GitHub убедись, что выбрана именно ветка `main`.

## 2. Деплой на VPS

После merge подключись к серверу и выполни одну команду:

```bash
/usr/local/bin/crowned-dogs-deploy
```

Скрипт сам:

1. Запрещает одновременный запуск второго деплоя через `flock`.
2. Проверяет каталог, `origin`, ветку `main` и отсутствие серверных правок.
3. Выполняет `git fetch origin main` и только fast-forward merge.
4. Устанавливает зависимости через `npm ci`.
5. Выполняет `npm run check` и `npm run web:build`.
6. Только после успешных проверок перезапускает `crowned-dogs-bot.service` и `crowned-dogs-web`.
7. Ждёт состояние `running healthy` и проверяет `https://app.4-i-7.ru/r2/`.

Серверный доступ к GitHub работает через отдельный deploy key **только для чтения**. Личный токен владельца на VPS не сохраняется.

## 3. Если деплой остановился с ошибкой

Не запускай его повторно вслепую и не делай `git reset --hard`.

Сначала посмотри состояние:

```bash
git -C /srv/crowned-dogs status
systemctl status crowned-dogs-bot.service --no-pager
docker logs --tail 80 crowned-dogs-web
```

- **Есть серверные правки:** сохрани и разберись с ними отдельно. Скрипт намеренно не перезаписывает их.
- **Ошибка Git:** проверь, не разошлась ли серверная ветка с GitHub. На сервере не должно быть ручных коммитов.
- **Ошибка тестов или сборки:** бот не перезапускается. Исправь код через обычный PR и затем повтори деплой.
- **Нет healthy:** смотри логи контейнера и состояние общего HTTPS-шлюза.

## 4. Откат ошибочной версии

Не стирай историю и не делай force push. Создай обычный revert-коммит через отдельную ветку и PR, дождись проверок и выполни тот же деплой:

```bash
git switch main
git pull --ff-only
git switch -c art/revert-problem-change
git revert SHA_ОШИБОЧНОГО_КОММИТА
npm run check
npm run web:build
git push -u origin HEAD
gh pr create --base main --fill
```

# Правила, которые сохраняют совместную работу предсказуемой

- Маленькие PR лучше больших накопленных изменений.
- Перед новой задачей всегда обновляй `main`.
- Не редактируй одну и ту же бинарную модель одновременно с другим человеком.
- Не коммить `node_modules`, `target`, `apps/web/dist`, `.env` и временные файлы.
- Не храни рабочие изменения только у себя неделями: отправляй ветку на GitHub, даже если PR ещё черновой.
- Не исправляй конфликт просто «чтобы Git пропустил»: после него обязательны проверки.
- Не запускай деплой во время чужого деплоя: скрипт это запрещает.

Проверка самого скрипта деплоя на безопасные сценарии:

```bash
bash infra/test-deploy.sh
```
