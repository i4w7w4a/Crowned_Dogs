# Online API: постоянный PvP runtime

Реализованы постоянные Telegram-аккаунты, профиль Rust и жетон, сессии, сохранённые бои, намерения изменения профиля, однократные награды и подтверждённый вход обычного браузера. Уровни ограничены 4. Новый runtime объединяет API, один Telegram poller и фоновые задачи. Старые UI/бот остаются отдельными путями до интеграции и выпуска; готовность сервера не заменяет приёмку двух реальных аккаунтов в 3D.

## Настройка

Нужны Node 22.18+, Rust/WASM по `LOCAL_BUILD.md`, отдельный PostgreSQL и роль с правами на миграции. Runtime-роли после миграции нужны SELECT/INSERT/UPDATE/DELETE таблиц и USAGE/SELECT последовательности outbox; DDL ей не требуется. Доступ к БД закрыт от внешнего интернета. Секреты хранить в защищённой конфигурации окружения, `.env` не коммитить.

Переменные (без значений): `ONLINE_DATABASE_URL`, `BOT_TOKEN`, `ONLINE_ORIGIN`; необязательные `ONLINE_HOST`, `ONLINE_PORT`, `API_BASE_PATH`, `NODE_ENV`. БД тестов задаётся только отдельной `ONLINE_TEST_DATABASE_URL`, никогда не через production-переменную. TLS PostgreSQL настраивается соединением и доверенным CA, проверку сертификатов не отключать.

Из корня репозитория:

```powershell
npm ci
npm run online:migrate
npm run online
```

Эти команды предназначены для подготовленной отдельной БД. Миграция не запускается автоматически при старте; `online:migrate` повторяемая, запускать одним мигратором. API по умолчанию слушает `127.0.0.1:3100`, маршруты `/api/online`. В production нужны HTTPS и `NODE_ENV=production`, чтобы cookie была Secure. `ONLINE_ORIGIN` — точный origin сайта без пути и завершающего `/`. `API_BASE_PATH=/r2/api/online` позволяет обслужить существующий сайт через его project Caddy без снятия `/r2`; cookie получает тот же Path. Менять Caddy/сервисы этот этап не требует.

## Контракт

| Метод и путь относительно API_BASE_PATH | Вход / результат |
|---|---|
| POST `/auth/telegram` | Только JSON `{ "initData": "raw signed Telegram data" }`; account и maxLevel, сессия только в cookie |
| GET `/me` | Свой серверный account и maxLevel; без сессии 401 |
| POST `/auth/logout` | Пустое тело или `{}`; отзыв текущей сессии, 204 |
| GET `/health` | 200 `{ "ok": true }` при доступной мигрированной БД, иначе 503 |

Вход открыт любому корректно подтверждённому Telegram ID; allowlist игроков нет. При отсутствии initData гостевой аккаунт не создаётся. HMAC проверяет все подписанные поля, кроме `hash`, включая `signature`, если оно присутствует. Допускаются возраст до 5 минут и будущий сдвиг до 30 секунд; часы сервера должны быть синхронизированы. Данные проверены при входе, сессия действует 8 часов без продления; повторный вход выдаёт новую сессию и обновляет имена, сохраняя ID/жетон/прогресс. Logout отзывает текущую сессию, остальные устройства сохраняют свою.

Сессия — 32 случайных байта; БД хранит SHA-256, cookie HttpOnly/SameSite=Lax, без Domain, Path равен API_BASE_PATH. POST требует точный `Origin`; credentialed CORS отсутствует. JSON ограничен 16 KiB; заголовки 16 KiB; таймаут получения запроса и заголовков 10 секунд, простаивающего сокета 15 секунд. Ответы не кэшируются. В логи не пишутся credentials/initData/строка БД. Клиентские level/xp/stats/tag и любые дополнительные поля входа отвергаются.

Игровые запросы после проверки сессии ограничены 240 запросами на **verified account.id** за минуту; общего IP-лимита на них нет. Два игрока за одним proxy/Wi-Fi не делят квоту. Для неавторизованных запросов — 1000/мин и 20 попыток входа/мин на IP; максимум 10 000 активных IP и аккаунтов. `X-Forwarded-For` не читается. Единственный допустимый адрес от proxy — `X-Crowned-Client-IP`, только если socket peer совпадает с конкретным IP из `ONLINE_TRUSTED_PROXY_IPS` (через запятую, по умолчанию пусто, CIDR не допускается). Неверный заголовок или недоверенный peer возвращает ключ к socket IP. Project Caddy обязан **замещать** этот заголовок; его собственное доверие к shared gateway настраивается отдельно одним точным адресом. Память лимитов теряется при рестарте и не общая между процессами.

Выдача жетона и регистрация/обновление аккаунта с созданием сессии — одна транзакция. Общая строка `online_tag_counters` блокируется `FOR UPDATE`; это намеренно сериализует входы. Rust `core.nextTag` определяет формат/месяц/ёмкость, существующие жетоны текущего призыва также учитываются. Rust `core.syncFresh`, `core.starterLoadout` и `client.look.normalize` задают прогресс/начальный комплект/внешность. При 999 занятых номерах следующая регистрация даёт 503 `tag_capacity_exhausted`, без частичного аккаунта или сессии; старые аккаунты продолжают входить. Расширение формата требует отдельного решения. Удаление аккаунтов и повторное использование номеров этот API не поддерживает.

## Проверки

```powershell
npm run check
npm run web:build
node --test apps/server/test/online-*.test.ts
```

Основные интеграционные тесты создают временный каталог и реальный embedded PostgreSQL PGlite, закрывают/открывают его для проверки сохранности и удаляют только свой проверенный временный путь. Тестовая зависимость PGlite не входит в production. Его одна connection сериализует транзакции: Promise.all подтверждает поведение хранилища, но **не доказывает гонки нескольких PostgreSQL connections/процессов**.

Для native-сценариев подготовить отдельную локальную БД `crowned_dogs_test` или `crowned_dogs_test_*`, задать только `ONLINE_TEST_DATABASE_URL`, выполнить `node --test --test-concurrency=1 apps/server/test/online-postgres.test.ts apps/server/test/online-pvp-postgres.test.ts`. Тесты отвергают удалённый host, другое имя БД и URL query overrides, создают свои случайные schema и удаляют только их. 6.11.2026 оба сценария пройдены на изолированном PostgreSQL 18.6: реальные гонки регистрации/принятия/команд, переподключение с сохранённым приказом, rollback наград, одноразовое потребление browser nonce и lease fencing. Без переменной явно skipped; Linux CI запускает их с PostgreSQL 18 service.

## Постоянный PvP runtime (#18)

Миграции `002_pvp.sql` и `003_browser_login.sql` добавляют бои, слоты, квитанции команд,
ledger наград, outbox и browser challenges. `npm run online:migrate` применяет их явно;
обычный запуск сам БД не мигрирует. `/health` требует актуальную миграцию 3.

`npm run online` теперь запускает API, один новый Telegram poller, deadline loop и outbox worker.
Помимо параметров основы требуются `ONLINE_BOT_USERNAME`, `ONLINE_WEBAPP_URL`, числовой
`ONLINE_CHAT_ID` и положительный `ONLINE_THREAD_ID`. Для выпуска оператор задаёт согласованную
группу и тему в приватной конфигурации. Вызовы идут только туда; на общий чат fallback отсутствует.
До запуска этого runtime старый бот должен быть остановлен, иначе два poller конфликтуют.
Main Mini App настраивается у бота; контракт и ограничения — [online-contract-v1.md](online-contract-v1.md).

Обычный браузер получает сессию только после явного подтверждения в личном чате Telegram.
Nonce остаётся в HttpOnly cookie и хеше БД; challenge действует 5 минут, consume одноразов.
Приглашение сохраняется через этот вход. Никакого гостевого входа или публичного dev-login нет.

`SIGINT`/`SIGTERM` прекращают новые итерации и HTTP-подключения, прерывают Telegram delivery,
дожидаются текущих задач и middleware poller, затем закрывают пул БД. Текущий outbox lease после
аварийного выхода восстанавливается. Сроки проверяются после SQL lock; рестарт разрешает один
просроченный ход и назначает следующий срок от текущего времени.

Короткие PvP-транзакции сериализованы одним row lock. Это пилотный компромисс, не результат
нагрузочной проверки. Квитанции сохраняют точный ответ, включая прежний serverNow; для свежего
состояния нужен GET. Invite version защищает игровые переходы; delivery status проверяется при
каждом poll независимо от изменения version. Чистка старых receipts/history и сессий — отдельная
операционная политика до роста аудитории; сейчас они не удаляются автоматически.

Новые проверки: `online-game.test.ts`, `online-game-http.test.ts`, `online-browser-login.test.ts`,
`online-outbox-storage.test.ts`, `online-pvp-postgres.test.ts`. Native файл использует тот же
guard `ONLINE_TEST_DATABASE_URL`, отдельную случайную schema и настоящие подключения. Общий
`npm test` ограничивает параллельность двумя файлами, чтобы несколько PGlite не исчерпали память.

## Перед production (все направления)

Ничего не развёрнуто и production-БД не изменялась. Сначала подготовить отдельную БД/роль/сервис и бэкап, проверить миграцию на копии и восстановление в чистую БД, определить допустимую потерю данных/время восстановления. До любых новых production-регистраций импортировать доверенные Telegram ID и жетоны из прежнего реестра и продвинуть счётчики. Старые жетоны/идентичность сохраняются, прогресс новый уровня 1; импорт ещё предстоит написать и проверить. Нельзя включать независимую выдачу жетонов старым ботом и новым API в одной production-аудитории до перехода на общее хранилище. Нужны native PostgreSQL тест, настройка proxy/лимитов/HTTPS, очистка просроченных/отозванных сессий и проверка двух реальных аккаунтов после соединения всех этапов. При смене правил профили и snapshots потребуют явных миграций.
