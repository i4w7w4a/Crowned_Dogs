# Online API: локальный фундамент

Реализован первый этап: постоянный Telegram-аккаунт, свежий профиль Rust, уникальный жетон, сессия и чтение профиля. Уровни ограничены 4. Нынешний 3D UI и Telegram-бои остаются на старых путях: UI хранит `cd-sync` локально, бот использует память и `OPERATORS_FILE`. Настройка внешности, снаряжения, очков, серверные награды, PvP и обычный браузерный Telegram-вход ещё не реализованы.

## Настройка

Нужны Node 22.18+, Rust/WASM по `LOCAL_BUILD.md`, отдельный PostgreSQL и роль с правами на миграции. Runtime-роли после миграции достаточно SELECT/INSERT/UPDATE этих таблиц; доступ к БД закрыт от внешнего интернета. Секреты хранить в защищённой конфигурации окружения, `.env` не коммитить.

Переменные (без значений): `ONLINE_DATABASE_URL`, `BOT_TOKEN`, `ONLINE_ORIGIN`; необязательные `ONLINE_HOST`, `ONLINE_PORT`, `API_BASE_PATH`, `NODE_ENV`. БД тестов задаётся только отдельной `ONLINE_TEST_DATABASE_URL`, никогда не через production-переменную. TLS PostgreSQL настраивается соединением и доверенным CA, проверку сертификатов не отключать.

Из корня репозитория:

```powershell
npm ci
npm run online:migrate
npm run online
```

Эти команды предназначены для подготовленной отдельной БД. Миграция не запускается автоматически при старте; `online:migrate` повторяемая, запускать одним мигратором. API по умолчанию слушает `127.0.0.1:3100`, маршруты `/api/online`. В production нужны HTTPS и `NODE_ENV=production`, чтобы cookie была Secure. `ONLINE_ORIGIN` — точный origin сайта без пути и завершающего `/`. `API_BASE_PATH=/r2/api/online` позволяет обслужить существующий сайт через его project Caddy без снятия `/r2`; cookie получает тот же Path. Менять Caddy/сервисы этот этап не требует.

## Контракт

| Метод и путь относительно API_BASE_PATH | Вход / результат |
|---|---|
| POST `/auth/telegram` | Только JSON `{ "initData": "raw signed Telegram data" }`; account и maxLevel, сессия только в cookie |
| GET `/me` | Свой серверный account и maxLevel; без сессии 401 |
| POST `/auth/logout` | Пустое тело или `{}`; отзыв текущей сессии, 204 |
| GET `/health` | 200 `{ "ok": true }` при доступной мигрированной БД, иначе 503 |

Вход открыт любому корректно подтверждённому Telegram ID; allowlist игроков нет. При отсутствии initData гостевой аккаунт не создаётся. HMAC проверяет все подписанные поля, кроме `hash`, включая `signature`, если оно присутствует. Допускаются возраст до 5 минут и будущий сдвиг до 30 секунд; часы сервера должны быть синхронизированы. Данные проверены при входе, сессия действует 8 часов без продления; повторный вход выдаёт новую сессию и обновляет имена, сохраняя ID/жетон/прогресс. Logout отзывает текущую сессию, остальные устройства сохраняют свою.

Сессия — 32 случайных байта; БД хранит SHA-256, cookie HttpOnly/SameSite=Lax, без Domain, Path равен API_BASE_PATH. POST требует точный `Origin`; credentialed CORS отсутствует. JSON ограничен 16 KiB; заголовки 16 KiB; таймаут получения запроса и заголовков 10 секунд, простаивающего сокета 15 секунд. Ответы не кэшируются. В логи не пишутся credentials/initData/строка БД. Клиентские level/xp/stats/tag и любые дополнительные поля входа отвергаются.

Ограничитель процесса: 120 запросов и 20 попыток входа на socket IP за минуту, максимум 10 000 активных IP. `X-Forwarded-For` не доверяется. За reverse proxy все клиенты видны одним peer IP: лимит станет общим; перед публичным включением настроить лимиты реальных клиентов на доверенном proxy и согласовать лимит API. Память лимитов теряется при рестарте и не общая между процессами.

Выдача жетона и регистрация/обновление аккаунта с созданием сессии — одна транзакция. Общая строка `online_tag_counters` блокируется `FOR UPDATE`; это намеренно сериализует входы. Rust `core.nextTag` определяет формат/месяц/ёмкость, существующие жетоны текущего призыва также учитываются. Rust `core.syncFresh`, `core.starterLoadout` и `client.look.normalize` задают прогресс/начальный комплект/внешность. При 999 занятых номерах следующая регистрация даёт 503 `tag_capacity_exhausted`, без частичного аккаунта или сессии; старые аккаунты продолжают входить. Расширение формата требует отдельного решения. Удаление аккаунтов и повторное использование номеров этот API не поддерживает.

## Проверки

```powershell
npm run check
npm run web:build
node --test apps/server/test/online-*.test.ts
```

Основные интеграционные тесты создают временный каталог и реальный embedded PostgreSQL PGlite, закрывают/открывают его для проверки сохранности и удаляют только свой проверенный временный путь. Тестовая зависимость PGlite не входит в production. Его одна connection сериализует транзакции: Promise.all подтверждает поведение хранилища, но **не доказывает гонки нескольких PostgreSQL connections/процессов**.

Для native-сценария вручную подготовить отдельную локальную БД с именем `crowned_dogs_test` или `crowned_dogs_test_*`, задать только `ONLINE_TEST_DATABASE_URL`, выполнить `node --test apps/server/test/online-postgres.test.ts`. Тест отказывается работать с удалённым host/чужим именем, создаёт свою случайную schema и удаляет только её. Проверяет реальные pg transactions/rollback/release, параллельные подключения и уникальность. Без переменной сценарий явно skipped; в этой среде native PostgreSQL отсутствует, сценарий не исполнялся.

## Перед production

Ничего не развёрнуто и production-БД не изменялась. Сначала подготовить отдельную БД/роль/сервис и бэкап, проверить миграцию на копии и восстановление в чистую БД, определить допустимую потерю данных/время восстановления. До любых новых production-регистраций импортировать доверенные Telegram ID и жетоны из прежнего реестра и продвинуть счётчики. Старые жетоны/идентичность сохраняются, прогресс новый уровня 1; импорт ещё предстоит написать и проверить. Нельзя включать независимую выдачу жетонов старым ботом и новым API в одной production-аудитории до перехода на общее хранилище. Нужны native PostgreSQL тест, настройка proxy/лимитов/HTTPS, очистка просроченных/отозванных сессий и проверка двух реальных аккаунтов после соединения всех этапов. При смене правил профили и snapshots потребуют явных миграций.
